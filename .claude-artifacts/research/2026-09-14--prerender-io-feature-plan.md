# Prerender.io feature analysis and Meelu implementation plan

Date: 2026-09-14. Research only; no code changes. Every claim about prerender.io or Google carries a URL. Claims about Meelu cite the file in this repo.

---

## 1. What prerender.io is, in one paragraph

Prerender.io is a hosted "dynamic rendering" service (in business "since 2014", "100,000+ businesses", https://prerender.io/). The customer installs a thin middleware at their CDN, reverse proxy or app server (Cloudflare Worker, Nginx, Apache, Express, Next.js `middleware.js`/`proxy.js`, Netlify extension, and ~25 others: https://docs.prerender.io/docs/integrations). The middleware inspects the `User-Agent` of every GET/HEAD request for an HTML resource; if it matches a maintained list of search, social, SEO-tool and AI crawlers, it proxies the request to `https://service.prerender.io/<original-url>` with an `X-Prerender-Token` header, and otherwise passes the request to the origin untouched (https://docs.prerender.io/docs/how-does-prerender.io-work, https://raw.githubusercontent.com/prerender/prerender-node/master/index.js). On a cache hit the service returns a stored, fully rendered HTML snapshot; on a miss it renders the page in headless Chrome, stores the result if the origin returned 200, and returns it to the crawler (https://docs.prerender.io/docs/how-prerender-caching-works). Snapshots expire on a plan-gated TTL and are refreshed by a normal queue (oldest first) and a priority queue fed by a sitemap crawler, a `/recache` API and manual dashboard actions (https://docs.prerender.io/docs/10-recaching). Pages can override the status code the crawler receives with `<meta name="prerender-status-code">` and `<meta name="prerender-header">`, and signal readiness with `window.prerenderReady` (https://docs.prerender.io/docs/best-practices-for-crawler-ready-pages). Google classifies the whole approach as "a workaround and not a long-term solution", recommends SSR/static rendering/hydration instead, and states it is not cloaking "as long as your dynamic rendering produces similar content" (https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering).

## 2. Feature inventory

Competitive context, cited so the fit judgement in §4 is grounded:
- SEO4Ajax's own comparison says prerender.io lacks multi-user accounts, SEO reports, HTTP-redirect caching, custom headers/UA, and retries (https://www.seo4ajax.com/compare/). Prerender's page says the reverse about pricing and caching intervals (https://prerender.io/prerender-vs-seo4ajax/).
- Rendertron is deprecated; prerender markets "in-advance" rendering, SEO score and crawl analytics against it (https://prerender.io/prerender-vs-rendertron/, https://www.ohmycrawl.com/rendertron-prerender-io/).
- Independent criticisms: every render counts against quota including 4xx/5xx and redirects; refresh frequency is plan-gated; UA lists need manual maintenance so new AI bots are missed; "control and management of cached pages can be lacking"; "clunky" (https://encited.com/blog/prerender-io-alternatives, https://www.capterra.com/p/238716/Prerender/reviews/).
- Cloudflare now sells the primitives directly: Browser Rendering `/crawl` returns HTML/Markdown/JSON for a whole site (https://developers.cloudflare.com/changelog/post/2026-03-10-br-crawl-endpoint/) and a documented "pre-render pages for crawlers" Worker recipe using the `/content` endpoint with `networkidle2`, cached via the Cache API (https://developers.cloudflare.com/browser-run/how-to/pre-render-pages/). AI Crawl Control changes defaults on 2026-09-15 to block Training and Agent crawlers on ad-bearing pages while Search stays allowed (https://www.helpnetsecurity.com/2026/07/02/cloudflare-ai-crawler-controls/).
- Google: dynamic rendering is a workaround, deprecated as a recommendation, tolerated, not cloaking if content is equivalent (https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering, https://www.seroundtable.com/google-search-updates-javascript-docs-36849.html). Cloaking is "presenting different content to users and search engines with the intent to manipulate search rankings" (https://developers.google.com/search/docs/essentials/spam-policies).

## 3. Diagnostic features we can match or beat locally

Meelu's render facts live in `site_page_renders` (`api/src/render_jobs/models/site_page_render.py`, one row per page per device), raw crawl facts in `site_pages` (`api/src/site_pages/models/site_page.py`), and rules in `api/src/technical_seo/rules/render.py` (26 kinds) and `ai_crawlers.py` (6 kinds). Snapshots are written by `app/src/main/render/index.js` to `<userData>/renders/<siteId>/<device>/<pageId>.html` and the path is stored in `html_path`.

### 3.1 Rendered vs raw comparison
- Prerender shows: nothing comparative. It only shows the cached HTML and a score computed on it (https://docs.prerender.io/docs/how-prerenders-seo-score-works).
- Meelu has: `js-only-content`, `js-only-title`, `js-only-canonical`, `js-only-h1`, `js-only-schema`, `js-only-links`, `robots-changed-by-js`, `canonical-changed-by-js`, `client-side-redirect`, `js-dependent-site`. These already implement what Google's JS-SEO guide warns about (canonical must equal the raw value; adding `noindex` by JS can stop rendering: https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).
- Gap: the user cannot *see* the two documents side by side; they see an issue line. Prerender's "View cached HTML" is a one-click preview.
- Implementation: add a `GET /api/v1/site/page-renders/html?page_id&device` endpoint that streams the file at `html_path` (the file is local, so this is served by the app over IPC, not the api; the api only knows the path). In the Pages screen add a "Rendered vs raw" panel: left = `site_pages.body_text`/`title`/`canonical`/`h1`, right = the same fields from `site_page_renders`, with the diff rows highlighted. No new tables.

### 3.2 Render status codes and "what Googlebot sees" preview
- Prerender shows: per-URL state, status, content age, source, "View cached HTML"; per-code explanations for 401/403/409/422/429/404/410/5xx/Cloudflare 52x (https://docs.prerender.io/docs/cache-manager, https://docs.prerender.io/docs/status-codes).
- Meelu has: `status`, `final_url`, `render_error`, `rendered_at`, `settle_reason`, `main_frame_navigations`, `html_path`, plus `site_pages.status`/`redirect_*`.
- Gap: no page-level render table in the UI, no status explanation, no snapshot preview.
- Implementation: a "Renders" tab on the Technical SEO desk listing `site_page_renders` joined to `site_pages` with columns URL, device, raw status, rendered status, settle reason, age (`now - rendered_at`), fresh (`rendered_from_hash = content_hash`), console errors, failed requests, and a "Preview as Googlebot" action that opens the snapshot in a sandboxed `<iframe sandbox>` with scripts disabled. Reuse the existing `GET /site/page-renders` and `render_status` endpoints in `api/src/render_jobs/endpoints.py`; add a `list` endpoint with paging and filters (device, status class, stale, has_errors) following the CLAUDE.md list-api shape. Put the status-code explanations into the technical-seo desk guide text, not the tool descriptions.

### 3.3 Missing and blocked resources
- Prerender shows: "resource logs" with 403/401 from third-party CDNs that reject its UA; guidance to allowlist its UA/IPs; a default block list of trackers (https://docs.prerender.io/docs/25-empty-or-partially-rendered-pages, https://docs.prerender.io/docs/services-blocked-ignored-by-prerender.io).
- Meelu has: `failed_requests`/`failed_samples`, `failed_data_requests`, `failed_scripts`/`failed_script_samples`, `blocked_assets`/`blocked_samples` (robots-blocked for Googlebot), `cors_errors`, `mixed_content_*`, `third_party_hosts`, `largest_resource_*`; rules `render-blocked-assets`, `render-failed-requests`, `third-party-bloat`.
- Gap: Meelu does not distinguish "blocked because robots.txt disallows Googlebot" from "blocked because the third party refused the bot UA" (403/401 on the sub-resource). Google's fix-guide lists robots-blocked JS as a top cause (https://developers.google.com/search/docs/crawling-indexing/javascript/fix-search-javascript).
- Implementation: in `app/src/main/render/page.js` the failed-sample entries already carry `url` and `type`; add `status` (from the debugger `Network.responseReceived`) and a `reason` enum (`robots`, `http_4xx`, `http_5xx`, `net`, `cors`). Store as-is in `failed_samples` (JSONB, no migration). Split `render-failed-requests` into `render-failed-scripts-forbidden` (a script returned 401/403/429 — "your CDN or WAF rejects Googlebot's UA") and keep the generic one. No new columns.

### 3.4 JavaScript errors
- Prerender shows: render logs in the dashboard, with the note that headless environments expose errors that depend on UA or geography (https://docs.prerender.io/docs/25-empty-or-partially-rendered-pages).
- Meelu has: `console_errors`, `console_samples`, `exception_count`; rule `render-console-errors`.
- Gap: none in data; the UI shows a count, not the samples with stack/source. Google recommends a global error handler and auditing (https://developers.google.com/search/docs/crawling-indexing/javascript/fix-search-javascript).
- Implementation: surface `console_samples` in the Renders tab row expander. Add a `desktop_only`/`mobile_only` flag in the rule text when `exception_count` differs by device (both rows exist; a SQL `where` in `_both`/`_mobile` helpers in `render.py`).

### 3.5 Mobile vs desktop
- Prerender shows: a mobile snapshot served to mobile crawler UAs, 2× render cost; no comparison between the two (https://docs.prerender.io/docs/8-desktop-vs-mobile).
- Meelu has: both device rows and 8 comparison rules (`mobile-js-only-content`, `mobile-hidden-content`, `mobile-hidden-links`, `mobile-viewport-overflow`, `mobile-small-tap-targets`, `mobile-title-differs`, `mobile-canonical-differs`, `mobile-noindex-differs`, site-level `mobile-differs-from-desktop`).
- Gap: none. Meelu is strictly ahead. Only note: prerender's mobile profile is Pixel 5 / Android 11 (https://docs.prerender.io/docs/33-overview-of-prerender-crawlers); Meelu's is Nexus 5X / Android 6 (`page.js`), which matches Google's documented smartphone UA and should stay.

### 3.6 Sitemap coverage of rendered pages
- Prerender shows: sitemap import, health, revisit interval, "source = Sitemap" per cached URL, and a troubleshooting page for URLs "not requested in the past 30 days" (https://docs.prerender.io/docs/sitemap, https://docs.prerender.io/docs/pages-that-have-not-been-requested-in-the-past-30-days).
- Meelu has: `site_pages.in_sitemap`, `site_pages.kind`, render `scope` = sample|all with per-kind sampling (`SAMPLE_PER_KIND` in `repository.py`).
- Gap: no view of "sitemap URLs never rendered / rendered stale".
- Implementation: extend `render_status` counts with `sitemap_eligible`, `sitemap_rendered`, `sitemap_fresh` (three more counts in `RenderCountsRecord`; SQL in `repository.py` adding `SitePage.in_sitemap.is_(True)`). Add a render scope `sitemap` next to `sample`/`all`. Site rule `sitemap-pages-unrendered` (p3) when `sitemap_fresh / sitemap_eligible < 0.9` after a full run. No new table.

### 3.7 Recache triggers on content change
- Prerender: TTL expiry, sitemap revisit, `/recache` API from the customer's deploy/CMS hooks; recommends "set high expiration values and selectively recache only modified pages" and warns that stale snapshots get Merchant Center listings disapproved (https://docs.prerender.io/docs/best-practices-for-crawler-ready-pages, https://docs.prerender.io/docs/mismatched-prices). Prerender itself cannot detect a change; the customer must tell it.
- Meelu has: change detection for free. The crawler stores `site_pages.content_hash`, `etag`, `last_modified`, `content_changed_at`; the render stores `rendered_from_hash`; freshness is `rendered_from_hash == content_hash` (`repository.py` lines 220–238, 340). This is the recache signal prerender charges for and asks customers to wire themselves.
- Gap: it is a query, not an event. Nothing subscribes to "hash changed → render this page again", and the raw-hash test misses the case where the raw HTML is a static shell and only the JSON the JS fetches changed.
- Implementation: (a) after a crawl job finishes, `app/src/main/crawler/index.js` already knows the changed page ids; enqueue a render job with a new scope `changed` (`SiteRenderJob.scope in {sample, all, sitemap, changed}`) whose candidate query is `rendered_from_hash IS DISTINCT FROM content_hash`; (b) add `rendered_content_hash_prev` to `site_page_renders` so a re-render can say whether the *rendered* content changed while the raw did not (the SPA-shell case) and drive a `render-content-drift` info rule: "rendered content changed on N pages whose raw HTML did not; a snapshot-serving setup would need a time-based recache for these". This is the one column addition in Phase 1.

### 3.8 Their SEO score and reporting
- Prerender shows: a per-page score from title, meta description, headings, OG tags, "other structural signals", computed on recache; a dashboard of crawl KPIs and an AI Insights health banner (https://docs.prerender.io/docs/how-prerenders-seo-score-works, https://docs.prerender.io/docs/ai-insights).
- Meelu has: issue tables `site_issues` / `site_page_issues` with `kind`, `severity`, `state`, `issue_type`, run-scoped, reviewed by the user or the agent; the `social_meta_count`, `title_count`, `description_count` render columns cover OG/title/description.
- Gap: no single "render health" roll-up per page or per site; no exportable report. The crawl-traffic half of their dashboard is impossible without being in the request path (see §4).
- Implementation: do not add a numeric score (prerender's own doc says not to optimise it). Add a site-level "Render health" card: counts of pages with `js-only-*`, `render-*`, `mobile-*` issues, share of pages fresh, share rendered with `settle_reason = timeout`. This is a query over existing issue tables; expose it as an api list endpoint filtered by `kind LIKE 'js-only-%'` etc. and as a desk-guide sentence, not a new tool. For "AI Insights" parity, the six `ai_crawlers.py` rules already produce the "access blocked" diagnostics that prerender's four checks (integration, robots.txt, CDN, WAF) cover; add the edge check to the rule text (`ai-crawler-blocked-at-edge` exists).

### 3.9 Things prerender's docs flag that Meelu should add as rules (all on existing columns)
- `soft-404-rendered`: `soft404_signal AND status = 200` (prerender's 404 Checker: https://docs.prerender.io/docs/404-checker; Google's soft-404 fix: https://developers.google.com/search/docs/crawling-indexing/javascript/fix-search-javascript). Fix text names both real fixes (server 404, or JS redirect to a 404 URL / `noindex`) and, only if the site later uses snapshot serving, the `prerender-status-code` meta.
- `render-timeout`: `settle_reason = 'timeout' AND pending_requests > 0` — prerender captures whatever exists at 20 s (https://docs.prerender.io/docs/25-empty-or-partially-rendered-pages); Meelu's WRS-like budget is 45 s. Message: "content still loading when the render budget ran out; N requests pending".
- `readiness-flag-missing`: only relevant once snapshot serving exists; skip until Phase 2.
- `render-status-meta-present`: detect `<meta name="prerender-status-code">` in the rendered head and report the value against the real HTTP status; a page whose meta says 404 but which is in the sitemap is a real bug for any prerender customer. Needs a new column `render_status_meta` (int, nullable) populated in `page.js`'s head scan next to `robotsMetaContents`. Small; include in Phase 1 because it also feeds Phase 2.
- `websocket-only-data`: `websocket_used AND failed_data_requests > 0` — Google's guide asks for HTTP fallbacks (https://developers.google.com/search/docs/crawling-indexing/javascript/fix-search-javascript). Column exists.
- `shadow-dom-content`: `shadow_dom_words > 0.5 * visible_word_count` — web components without `<slot>` (same Google page). Column exists.

## 4. Serving features (the fix half)

What a snapshot server must do, distilled from prerender's docs, regardless of which option Meelu picks:
1. Detect crawlers by UA on GET/HEAD for HTML-like paths, skipping 47 static extensions and `_escaped_fragment_`/`x-bufferbot` legacy triggers (https://raw.githubusercontent.com/prerender/prerender-node/master/index.js). Maintain the list; critics say stale lists miss new AI bots (https://encited.com/blog/prerender-io-alternatives). Optionally verify Googlebot by reverse DNS or Google's published IP JSON (https://developers.google.com/search/docs/crawling-indexing/verifying-googlebot); on Cloudflare, verified-bot categories (Search, Agent, Training, SEO, Social/Link Preview…) are available to rules (https://developers.cloudflare.com/bots/concepts/bot/verified-bots/categories/).
2. Return the correct status: 200 for a cached 200; honour `prerender-status-code` / `prerender-header` for 404/410/301 (https://docs.prerender.io/docs/best-practices-for-crawler-ready-pages); never store non-200 (https://docs.prerender.io/docs/how-prerender-caching-works); drop entries that turn 4xx or 3×5xx (https://docs.prerender.io/docs/10-recaching).
3. Mark responses (`X-Prerender-Request-ID`, `X-Prerender-Mode`) and set a short `Cache-Control` on a miss so CDNs do not pin a bad response (https://docs.prerender.io/docs/edge-cdn-status-codes-and-behaviour). Meelu's equivalents: `X-Meelu-Snapshot: hit|miss|bypass`, `X-Meelu-Snapshot-Age`.
4. Fail open: on any error serve the origin (`ctx.passThroughOnException()` in the Cloudflare worker: https://raw.githubusercontent.com/prerender/cloudflare/main/worker.js).
5. Avoid loops: never treat your own renderer's UA as a crawler (prerender's 502 "Prerender loop detected": https://docs.prerender.io/docs/edge-cdn-status-codes-and-behaviour). Meelu's render UA contains `MeeluSEO/1.0` (`page.js` line 11) which the middleware must exclude.
6. Snapshot hygiene: strip `<script>` tags except `application/ld+json` (the open-source server's `removeScriptTags` plugin: https://github.com/prerender/prerender), keep canonical/robots/hreflang exactly as rendered, inject `<base href>` if relative URLs were used, add nothing that is not on the live page. Equivalence is the entire cloaking defence (https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering, https://developers.google.com/search/docs/essentials/spam-policies).
7. Readiness: honour `window.prerenderReady === false` until it flips, then wait briefly (https://docs.prerender.io/docs/25-empty-or-partially-rendered-pages). Meelu's renderer should read the same flag so that customers coming from prerender keep their instrumentation.
8. Invalidation: the raw `content_hash` change (§3.7) plus a time-based ceiling for shell-only SPAs, plus a manual "recache these URLs" action.

### Option (a): Static snapshot export bundle + customer-deployed middleware
- Shape: the desktop app renders (already does) and exports `snapshots/<host>/<device>/<sha1(path)>.html` plus `manifest.json` (url → file, status, rendered_at, content_hash, device, canonical) into a folder the user uploads to wherever their site already lives (S3, R2, a `/_snapshots` directory on the origin). Meelu ships three generated snippets, with the site's sitemap-derived path allowlist baked in: a Cloudflare Worker (UA regex + extension skip + `fetch(SNAPSHOT_BASE + key)` + fallthrough), an Nginx `map $http_user_agent $is_bot` + `try_files`/`proxy_pass` block modelled on prerender-nginx (https://docs.prerender.io/docs/nginx-1), and an Express/Next `middleware.js`/`proxy.js` file (https://docs.prerender.io/docs/nextjs).
- Must exist: exporter module in the app (`app/src/main/render/export.js`), a manifest format, a page-level "include in snapshot bundle" flag, a status-code convention in the manifest (404/301 rows produce a tiny stub the middleware maps to the status; the `prerender-status-code` meta is read by Meelu at render time and written to the manifest), a UA list Meelu maintains and re-emits into every generated snippet, a "verify" action in the app that fetches the site with a Googlebot UA and checks for `X-Meelu-Snapshot: hit`, and the recache signal: the app re-exports only rows whose `content_hash` changed and prints the list of changed keys so the user's deploy script can purge them.
- Effort: 3–4 weeks (1 exporter + manifest, 1 three snippets + verify, 1 UI + docs, buffer).
- Running cost to Meelu: zero. To the customer: object storage and a Worker/edge function on their own bill.
- Risk: freshness depends on the user re-running the app; a laptop that is closed for a month serves month-old snapshots. Mitigated by a manifest `max_age` the middleware honours (serve origin, not a stale snapshot, when older than N days) and by the scheduled crawl that already exists locally. Second risk: a page that changed at the JSON layer but not the raw HTML (SPA shell) is never re-exported unless §3.7's time ceiling applies. Third: bot lists go stale in deployed snippets; the verify step should diff the deployed snippet's list version against Meelu's.

### Option (b): Meelu-hosted render endpoint + npm/pip middleware (the prerender.io model)
- Shape: `service.meelu.app/<url>` with a per-site token; Meelu runs headless Chrome in the cloud, caches, recaches on TTL and sitemap, exposes a recache API, and ships `meelu-node`, `meelu-python`, a Worker and Nginx/Apache configs — the full prerender.io surface (https://docs.prerender.io/docs/integrations, https://docs.prerender.io/docs/6-api).
- Must exist: everything in (a) plus a public multi-tenant edge with a global cache, a render farm with queueing, per-site auth, IP allowlist publication (customers' WAFs must allow Meelu's renderer, as they do prerender's: https://docs.prerender.io/docs/33-overview-of-prerender-crawlers), abuse controls (an open renderer is an open proxy; Cloudflare's recipe insists on a hostname allowlist: https://developers.cloudflare.com/browser-run/how-to/pre-render-pages/), quota metering and billing, uptime SLA and status page (prerender publishes maintenance: https://docs.prerender.io/docs/keep-track-of-prerender-service-maintenance), 24×7 on-call.
- Effort: 12–20 weeks to a credible beta; ongoing operations forever.
- Running cost: compute per render (prerender's overage is $1.25–$2 per 1,000 renders, which is the floor of their cost plus margin: https://prerender.io/pricing/), egress, storage per snapshot × devices, plus people.
- Risk: it is a hosting business, in direct competition with a 12-year incumbent and with Cloudflare's own Browser Rendering (https://developers.cloudflare.com/changelog/post/2026-03-10-br-crawl-endpoint/), for a technique Google says is a workaround (https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering). It contradicts the repo's "nothing is in production / no hosted infrastructure in front of the user's site" posture. Also breaks Meelu's local-render advantage: a cloud renderer needs the customer to allowlist it, which is the number-one prerender support topic (403/504: https://docs.prerender.io/docs/how-can-i-whitelist-prerenders-ip-addresses-and-user-agents).

### Option (c): Generate-and-upload to the customer's own object storage from the desktop app
- Shape: option (a) with the upload step done by the app through a provider adapter (S3 / R2 / GCS) in `app/src/main/providers`, keyed by the user's own credentials in the vault, exactly the pattern DataForSEO and Postproxy use per CLAUDE.md. The app writes the bundle, uploads changed objects, and purges via the storage API; the customer still deploys one of the generated middleware snippets pointing at the bucket URL. The api stores only the export state (which page/device/hash was uploaded when); it never touches the bucket.
- Must exist: (a) plus a `SnapshotStore` facade with S3-compatible and R2 adapters (R2 is S3-compatible, so one adapter with endpoint config), credential UI, an `export_state` per render (see §5 Phase 2 table), and a scheduled "export changed" run hooked to the existing local schedules.
- Effort: (a) + 1–2 weeks.
- Running cost to Meelu: zero. To customer: cents of storage.
- Risk: same freshness risk as (a), reduced because upload is automatic on every scheduled crawl+render; credential handling risk contained by the vault pattern already in place.

### Recommendation for v1: option (c), built as (a) plus an upload adapter, in that order
Why: the recache signal Meelu already owns (`content_hash` → `rendered_from_hash`) is the piece prerender customers have to build themselves, and it only pays off if the export is automatic, which is (c). (a) alone leaves the user copying folders. (b) is a different company. (c) keeps every byte on the customer's infrastructure, which is also the cleanest answer to the cloaking question: the snapshots are the same files the user can open in Meelu's "Preview as Googlebot" and diff against the raw page, so equivalence is auditable. Ship (a) first because (c) depends on it and (a) is testable without any vendor.

## 5. Phased plan

### Phase 1 — Diagnostics parity, no infrastructure (3 weeks)
User-visible outcome: a Renders tab on the Technical SEO desk with a per-page/per-device table, a Googlebot preview of any snapshot, a rendered-vs-raw diff panel, six new rule kinds, and a "render health" roll-up; automatic re-render of pages whose content changed.

Tables/columns:
- `site_page_renders`: add `render_status_meta int null`, `rendered_content_hash_prev text null`. One Alembic revision.
- `site_render_jobs.scope`: allow `sitemap` and `changed` (string column; no migration, service validation only).
- `failed_samples` entries gain `status` and `reason` keys (JSONB, no migration).

Endpoints (api):
- `GET /api/v1/site/page-renders/list` with paging and filters `device`, `status_class`, `stale`, `has_errors`, `in_sitemap`, `q`.
- `render_status` counts gain `sitemap_eligible`, `sitemap_rendered`, `sitemap_fresh`, `timed_out`.
- Preview is served by the app over IPC from `html_path` (file is local); the api does not stream files.

Rules (`api/src/technical_seo/rules/render.py`): `soft-404-rendered`, `render-timeout`, `render-failed-scripts-forbidden`, `render-status-meta-mismatch`, `websocket-only-data`, `shadow-dom-content`, `render-content-drift`, site-level `sitemap-pages-unrendered`.

App modules: `app/src/main/render/page.js` (read `window.prerenderReady`, capture sub-resource status, scan `prerender-status-code` meta), `app/src/main/render/index.js` (scopes `sitemap`/`changed`; trigger `changed` after crawl), dashboard Renders tab + diff panel + preview iframe.

Agent gets: the new columns and rules through the existing SQL surface (no new tool); the technical-seo desk guide gains three sentences: what `settle_reason` means, that the rendered-vs-raw diff exists on the Renders tab, and the meaning of `render_status_meta`. No tool names in prompts per CLAUDE.md.

Acceptance: (1) for a known SPA test site, `js-only-content` pages show a diff panel where the raw side is empty and the rendered side has text; (2) a page whose fixture returns 200 with "Page not found" is flagged `soft-404-rendered`; (3) changing a fixture page's HTML and re-crawling enqueues exactly that page under scope `changed`; (4) `render-timeout` fires on a fixture that never resolves a fetch; (5) preview renders the stored file with scripts disabled and no network calls to the origin.

Open decisions for the user: keep the 45 s page budget or align nearer prerender's 20 s and Google's unknown budget; whether the `sitemap` scope replaces `sample` as the default; whether to show `prerender-status-code` guidance at all in Phase 1 (only meaningful for sites already on a prerender vendor).

### Phase 2 — Snapshot export + customer-deployed middleware, then own-storage upload (5–6 weeks)
User-visible outcome: a "Serve snapshots to crawlers" screen on the Technical SEO desk: choose pages (default: sitemap pages, both devices), export a bundle or connect an S3/R2 bucket, copy a generated Worker / Nginx / Express-Next snippet with the site's allowlist and Meelu's bot list embedded, press Verify, and see "N pages served, M stale, last export at T".

Tables/columns (api):
- `site_snapshot_configs` (one per site): `enabled bool`, `devices text[]`, `path_allowlist text[]`, `max_age_days int`, `strip_scripts bool default true`, `bot_list_version text`, `store_kind text` (`bundle` | `s3` | `r2`), `store_base_url text`, `middleware_kind text`.
- `site_snapshot_exports` (one per page per device): `page_id`, `device`, `exported_hash`, `exported_at`, `object_key`, `status_served int`, `purged_at`. Unique on (`page_id`,`device`).
- Credentials never in the api; vault in the app.

Endpoints: CRUD on `site_snapshot_configs`; `list` on `site_snapshot_exports` with filters `stale`, `device`; `POST /site/snapshot-exports/mark` for the app to record an upload/purge batch.

App modules: `app/src/main/render/export.js` (bundle writer: strip scripts except ld+json, inject `<base>`, write stub for 404/301 rows, manifest), `app/src/main/providers/snapshot-store/` (S3-compatible adapter; R2 via endpoint), `app/src/main/render/verify.js` (fetch with Googlebot UA, expect `X-Meelu-Snapshot: hit`, compare title with snapshot), snippet templates for Cloudflare Worker, Nginx map, Express/Next `middleware.js`/`proxy.js`, and a bot-list JSON that Meelu maintains and versions.

Conventions: UA list = prerender-node's list minus `MeeluSEO`; skip prerender's 47 extensions; honour `prerender-status-code`/`prerender-header` exactly (so customers migrating from prerender change nothing in their pages); `window.prerenderReady` honoured at render time; response headers `X-Meelu-Snapshot`, `X-Meelu-Snapshot-Age`; on miss or age > `max_age_days` fall through to origin with `Cache-Control: no-store`; never serve a snapshot for a path outside the allowlist.

Agent gets: read access to `site_snapshot_configs` and `site_snapshot_exports` via SQL; one write tool on this desk, "re-export these URLs" (calls the desk service which flags rows for the app's next export run), tagged `meelu/writes`. The guide names the screen, not the tool.

Acceptance: (1) with a fixture site behind the generated Worker on a test zone, `curl -A Googlebot` returns the snapshot with `X-Meelu-Snapshot: hit` and a normal UA returns the origin; (2) a 404 fixture with the meta tag is served as 404; (3) changing one page and running the scheduled crawl+render+export uploads exactly one object and purges its key; (4) a snapshot older than `max_age_days` falls through to origin; (5) the rendered-vs-raw diff for every exported page shows only script removal (cloaking audit).

Open decisions: which middleware to ship first (Cloudflare Worker is the smallest and prerender's own recommended "closest to the visitor" layer: https://docs.prerender.io/docs/what-should-i-do-if-i-receive-a-prerender-integration-not-detected-error); whether to verify Googlebot by IP in the Worker (cost: a fetch of Google's JSON per cold start) or trust UA like prerender does; default `max_age_days`; whether social/link-preview bots are in the default list (they are in prerender's; OG tags are usually raw, so it may be unnecessary); pricing, if any, for this feature.

### Phase 3 — Hosted endpoint, if ever
Only if Phase 2 telemetry shows many users who cannot deploy any middleware and cannot use a bucket. Outcome would be option (b). Tables: multi-tenant snapshot store, tokens, quotas, request logs (this is what finally enables prerender's crawl-analytics dashboard, feature #12). Agent gets: crawl-traffic tables. Acceptance and decisions are moot until a business decision is made; the prerequisite is a deliberate reversal of "no hosted infrastructure in front of the user's site". Not planned.

## 6. Things to deliberately not copy

- **The hosted render farm and per-render pricing.** It is a hosting business with 24×7 obligations; incumbents and Cloudflare already own it; renders of 4xx/5xx and redirects being billable is the top customer complaint (https://encited.com/blog/prerender-io-alternatives). Meelu's cost model is a desktop app.
- **Plan-gated freshness (TTL ranges by tier, rule counts by tier).** Meelu has a real change signal; time-based expiry is a fallback ceiling, not the product (https://docs.prerender.io/docs/custom-cache-expiration).
- **A numeric SEO score.** Prerender's own doc says to use the breakdown "not to optimize the number itself" (https://docs.prerender.io/docs/how-prerenders-seo-score-works); Meelu already has issue rows with severity and state.
- **Crawl-traffic analytics as a promise.** It requires being in the request path. Do not fake it from crawl data; add it only if Phase 3 ever happens or via server-log import as a separate feature.
- **The GSC "integration".** It only pulls sitemaps (https://docs.prerender.io/docs/integrating-google-search-console-with-prerender); Meelu's crawler reads sitemaps directly and its GSC desk does more.
- **Blocking analytics/trackers in Meelu's renders.** Prerender blocks GA/GTM etc. to keep customers' analytics clean and renders fast (https://docs.prerender.io/docs/services-blocked-ignored-by-prerender.io); Meelu's purpose is to see what Googlebot sees, and Googlebot does not block them. Keep the block list only in the *export* renderer if a customer asks, never in the diagnostic render.
- **"Location-specific rendering", IP allowlists, reverse-DNS names.** Artifacts of rendering from someone else's data centre (https://docs.prerender.io/docs/33-overview-of-prerender-crawlers). Meelu renders from the user's machine.
- **Presenting dynamic rendering as the fix.** Google calls it a workaround and recommends SSR, static rendering or hydration (https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering); independent reviewers agree (https://www.ohmycrawl.com/rendertron-prerender-io/, https://www.jasminedirectory.com/blog/dynamic-rendering-is-it-still-relevant-in-2026/). Every Meelu issue text and the export screen should state the durable fix first and snapshot serving as the bridge.
- **Serving anything to bots that the user cannot see rendered.** The cloaking rule is content equivalence (https://developers.google.com/search/docs/essentials/spam-policies); the snapshot must be the same file the diff panel shows, with scripts stripped and nothing added.
- **`_escaped_fragment_` and `x-bufferbot` triggers** in prerender-node (https://raw.githubusercontent.com/prerender/prerender-node/master/index.js). The AJAX-crawling scheme has been dead for years; do not carry it into generated snippets.
- **Social-preview bots in the default serve list** unless a rule shows OG tags are JS-only on the site; `social_meta_count` on the rendered row versus the raw head tells the answer per site.
