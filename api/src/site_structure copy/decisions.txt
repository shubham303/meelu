WHY THIS MODULE EXISTS

A clone of api/src/site_structure, rebuilt bottom-up to understand the feature
and fix the defects found while reading it. Same package, class, table and
function names as the original, so the cutover is: delete site_structure,
rename this directory over it, ship one migration. Only what a defect forces
is allowed to differ.


THE SHARED TIER

Decided: a pipeline/ package as a peer of links/ and pillars/, owning the
lifecycle vocabulary (SuggestionState and its groupings), the shapes both
subfeatures pass around (ScreenResult, RankResult, ReconcileResult,
ReviewBatch, ReviewItem, ReviewResult), the 0.8 confidence rule, the
("ready", "llm_rejected") verdict set, the workspace-table name check and the
page-gone predicate. The alternative - pushing everything down and letting
pillars/* import from links/* the way the original does - is what produced the
sideways private imports listed below as a defect.

pipeline/ is not written yet. Until it is, links/ keeps its own ReconcileResult
and page-gone predicate and the root constants.py keeps SuggestionState; all of
it moves when pipeline lands.

The shared screen and review loops go in last, after pillars/ exists. Extracting
a loop from one call site is guessing at the protocol.


RULES THE UNWRITTEN LAYERS MUST HONOUR

- Higher is better, for every score column, enforced at the write. A removal
  stores 1 - relevance, so an unrelated link scores high because it is a better
  removal candidate. No reader flips a polarity, and nothing coalesces a NULL
  to 1.0 to guess a direction.
- NULL sorts last. NULL confidence means unscreened, NULL score means unranked;
  both rank below any real value. Ranking treats a missing confidence as the
  worst case instead of skipping the factor, so skipping the screen can never
  beat passing it. List queries order NULLS LAST.
- SETTLED_STATES (done, user_rejected) is the user's decision. No automated
  step - screen, review, rank, reconcile - may write over a row in it, including
  when it is named explicitly by id.
- pillar_page_suggestions.member_key is the hash of the sorted member_page_ids.
  Its definition lives in exactly one function, and the cutover migration's
  backfill has to compute the same value.


DEFECTS STILL TO FIX, AND WHERE THEY LAND

- links/ranking: score drafts only. In the original open_candidates includes
  ready and update_scores flips every cut row to llm_rejected, so a second run
  can un-publish a row the user has already seen. A ready row should count as
  spent budget, not as a candidate. OPEN QUESTION: scope ranking to the current
  job or keep it site-wide over drafts.
- links/ranking: the bulk score UPDATE carries site_id. The original's
  update_scores updates rows by id alone.
- links review inputs: de-duplicate the site_page_links join. A page pair with
  three body links yields three identical review items, so three LLM calls and
  three verdicts for one row.
- Both screening modules: the site_id a write uses is the caller's, not
  `caller.site_id or ""`.
- N+1s to fold into single queries: unlinked mentions (one query per target x
  phrase, one insert per target, and limit_per_target actually applies per
  phrase); link removals (anchor_chunk + edge_relevance per candidate inside
  the loop); pillar reconcile (whole link map and every page's changed_at pulled
  into Python).
- Tool signatures take their defaults from the PILLAR_* constants instead of
  repeating 4, 0.35 and 5 as literals.
- pillars must not reach into another package's privates. The original imports
  _count, _now and _page_gone from the links repository.


WHAT CHANGED FROM THE ORIGINAL'S BEHAVIOUR

- Reconcile marks instead of deletes: a satisfied suggestion becomes done, one
  whose page is gone becomes stale, and only rows in OPEN_STATES are touched.
  The original DELETEd all three cases, so a row the user had acted on vanished
  and came back as a fresh draft on the next run, and link suggestions never
  reached 'stale' at all. ReconcileResult loses its `removed` count.
